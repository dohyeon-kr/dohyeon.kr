# 인풋 하나를 추가하면 무엇이 같이 생길까?

**템플릿:** Aurora Explain · HyperFrames (aurora-explain)

원본: [candidate-02.json](candidate-02.json)

JSON에서 자동 생성한 검토용 스토리보드입니다. 수정은 원본 JSON에 반영한 뒤 다시 생성하세요. 연출 설명은 기획 의도이며, 실제 배치·동작은 렌더된 스냅샷과 영상으로 확인합니다. 음성 생성 전이므로 재생 시간은 확정하지 않습니다.

**첫 문장:** 회원가입에 휴대폰 번호 인풋을 하나 추가해 주세요.

**기획 의도:** 같은 휴대폰 입력 요소에 기능을 누적한다. 화면의 빠른 입력 안내와 서버의 재검증·인증 확인을 구분하고, 요청 형식과 오류 사유를 구체적인 예시로 보여준다. 자막과 모션은 일치하는 prepared 음성의 beat 시각을 따른다.

**원문:** [회원가입에 휴대폰 번호 인풋을 추가해주세요](<https://blog.dohyeon.kr/>)

## 1. 도입 —

**내레이션**

기획자가 말합니다. 회원가입에 휴대폰 번호 인풋을 하나 추가해 주세요. 바로 만들기 전에 먼저 묻습니다. 이 번호는 왜 받나요? 연락처인가요, 본인 인증인가요? 본인 인증용이라는 답이 오면 화면이 달라집니다. 인증번호 발송, 재전송, 만료와 실패 상태가 같이 생깁니다. 입력창은 하이픈과 공백을 걷어 내고, 길이가 맞는지 바로 알려줍니다. 하지만 화면의 검사만 믿을 수는 없습니다. 서버는 번호 형식을 다시 검사하고, 인증 완료 여부를 확인합니다. 숫자만 보낼지 국가 코드를 붙일지, 요청 형식도 맞춥니다. 중복 번호와 인증 만료는 구분해서 응답하고, 화면은 그 이유를 보여줍니다. 마지막으로 기존 회원을 봅니다. 기존 데이터에는 번호가 없는데 신규 회원만 필수라면, 그건 인풋 문제가 아니라 제품 정책입니다. 프론트엔드에서 인풋 하나를 추가한다는 건, 컴포넌트 하나를 놓는 일이 아니라 사용자 흐름 하나를 완성하는 일입니다.

**화면 구성**

- 주 문구:
- 배치: 도식을 중앙에 배치
- 전달할 관계: 하나의 input에서 시작해 인증, validation, API 오류, 기존 회원 정책으로 고려 범위가 늘어난다.
- 표현 방식: 공간 도식 — 하나의 회원가입 폼에 기능과 정책이 점진적으로 추가된다.
- 표현 이유: 단일 입력 요소가 커지고 상태가 바뀌는 것이 주제이므로 별도 사진이나 B-roll로 끊지 않는다. signup-phone-number-input-v2 구성이 명시적 렌더 계약이다.

**연출 흐름**

- 시작: 화면 중앙의 큰 회원가입 폼에 휴대폰 번호 입력창 하나가 놓인다.
- 사건: 목적, 인증, 입력 정규화, 서버 검증과 오류 응답, 기존 회원 정책이 순서대로 구체화된다.
- 변화: 준비된 beat 경계에 맞춰 같은 input의 값·오류·인증 상태가 바뀐다. 인증 필드가 추가되면서 폼 배경이 늘어나고 카메라가 연속해서 이동한다.
- 유지: 전화번호 input DOM은 본문 내내 유지한다. 제목과 자막은 고정된 안전 영역에 놓고, 폼 외곽만 화면 경계를 넘을 수 있다.
- 결과: 처음의 인풋 하나가 인증 UI와 오류 처리, API 계약, 기존 회원 정책 체크리스트까지 확장되어 프론트엔드가 완성해야 하는 실제 사용자 흐름으로 보인다.

2. 추가 연출 지시: grow-auth-fields

## 게시 문구

“회원가입에 휴대폰 번호 인풋을 추가해주세요.” 프론트엔드에서는 이 한 줄이 입력창 하나로 끝나지 않습니다. 왜 받는지, 인증이 필요한지, 어떤 오류를 처리할지, 서버와 어떤 계약을 맺을지, 기존 회원은 어떻게 할지에 따라 같은 화면이 계속 달라집니다.
